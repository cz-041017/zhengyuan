1. **先检索、再推理、后动手**：重读 `README.md`、本文档、`src/traffic_control/` 全部源码、`configs/` 全部配置、`tests/` 全部测试，确认当前实现边界与假设。

3. **先安全后优化**：任何评分、绿波、需求优化都**不得绕过**硬约束（冲突互锁、最小绿、最大绿、清空时序、P0 等待截止、P1 下游溢流）。

6. **改动即更新文档**：涉及算法、配置、安全约束的改动，同步更新本文档与 README 的「现状/路线图」。

## 1. 项目概述

**项目名**：smart-traffic-control（逻辑决策层，版本 0.1.0）
**语言/环境**：Python ≥ 3.11，uv 管理依赖（[`pyproject.toml`](../pyproject.toml)、[`uv.lock`](../uv.lock)）
**仓库**：<https://github.com/cz-041017/zhengyuan>

本项目是**纯视觉智能交通信号控制系统的逻辑决策层**：感知层用 YOLO11 识别停止线前等待车辆并计数（VehicleObservation），
决策层接收计数与时间戳，经「数据校验 → 状态估计 → 安全约束与优先级仲裁 → 相位选择 → 配时控制」，
输出**「建议的下一相位」PhaseDecision**，由控制接口层转发给执行层（PLC / 仿真器）。

### 1.1 四层架构

```
感知层 Perception   —— YOLO11 目标识别（车辆数、车道、时间戳、置信度、下游拥堵观测）
        │ VehicleObservation
逻辑决策层 Logic    ◀—— 本项目
        │ PhaseDecision（建议，非灯色指令）
控制接口层 Interface —— GB/T 20999 / GA/T 1049.2 通信协议对接
        │ 控制指令 / 执行反馈
执行层 Execution    —— PLC / 交通信号仿真器
```

> **分层边界**：决策层只输出「建议的下一相位」，**不直接生成灯色指令**；
> 实际灯色与相位切换必须由信号机执行并回传**可信反馈**后才更新内部状态。

## 2. 相位分组模型

决策层把「交通方向 movement」合并为「信号相位 phase」。一个相位 = 一组**能同时放行且通过冲突校核**的交通流集合。

### 2.1 模式 A：四向均为支路（无主路、无绿波）

每向「直行 + 左转」合并为 1 组，共 **4 组**，全部通过 score 对比：

| 组 | 放行方向 | 评分方式 |
|---|---|---|
| P1 | 北向 直行 + 左转 | score |
| P2 | 东向 直行 + 左转 | score |
| P3 | 南向 直行 + 左转 | score |
| P4 | 西向 直行 + 左转 | score |

### 2.2 模式 B：存在城市主路（设主路为南北向，方向可配置）

| 组 | 放行方向 | 评分方式 |
|---|---|---|
| P_MT | 主路**双向直行**（北直 + 南直） | **绿波优先（P2）** |
| P_ML | 主路**双向左转**（北左 + 南左） | score 比对（P3） |
| P_E | 东支路 直行 + 左转 | score 比对（P3） |
| P_W | 西支路 直行 + 左转 | score 比对（P3） |

> **安全要点**：支路「直行 + 左转」合并的前提是支路左转与对向支路直行**不存在放行冲突**，
> 否则必须拆分为独立相位，冲突关系来自**经审核的路口相位冲突表**，不能靠假设。

## 3. 决策流程总览（先约束，后优化）

每个决策周期（tick）执行以下四步：

```
① 硬约束过滤 —— 得到可行相位集合 F(t)
   冲突互锁有效 ∧ 切换时序有效(最小绿已满足) ∧ 信号机允许执行 ∧ 下游不拥堵(P1)
② 硬抢占判断 —— P0 等待截止 / 最大绿 触发时，走预定义约束路径（不参与评分）
③ 软评分排序 —— 仅对 F(t) 内相位计算 S(p)，取最高分（带滞回与去抖）
④ 切换握手 —— 触发 15s 倒数 → 复核 → 黄灯/全红清空 → 新相位 → 等反馈确认
```

**核心原则**：score **没有灯色权限**，只能在 F(t) 内排序；硬约束与硬抢占**不能被任何 score 数值抵消**。

## 4. P0–P3 优先级模型与 score 赋值

优先级语义顺序：**P0 > P1 > P2 > P3**。它不是单条数值刻度，而是「结构优先级」：
P0/P1 主要由**硬约束 + 硬抢占**保证，score 只作为预警/兜底。

### 4.1 每方向（每组）的输入量

- `N`：排队车辆数（YOLO11 停止线前等待计数，经 QueueEstimator 聚合）
- `W`：该方向**最老等待时间** `oldest_wait_s`（秒，边缘返回 ≥1 辆车时开始累计）
- `O`：下游路口拥堵观测值（下一路口的 YOLO11 返回）
- `D` = 120s（`optimization.max_wait_target_s`，等待硬指标）

组的聚合：`N_p = Σ(成员方向 N)`，`W_p = max(成员方向 W)`，`O_p = max(成员方向 O)`。

### 4.2 相位评分公式（初值，待标定）

```
S(p) = S_demand(p) + S_gw(p) + S_wait(p) + S_spill(p)
```

| 项 | 公式（初值） | 取值范围 | 优先级 |
|---|---|---|---|
| S_demand（P3 需求） | `0.6·min(N/N_max,1) + 0.4·min(W/D,1)`，N_max=20 | [0, 1] | P3 |
| S_gw（P2 绿波） | 主路直行相位处于绿波窗口内时 `+2.0`，否则 0 | {0, +2.0} | P2 |
| S_wait（P0 软预警） | `5.0 · clip((W − 80)/40, 0, 1)²` | [0, +5.0] | P0 |
| S_spill（P1 硬压制） | 任一下游方向拥堵时 `−1000`，否则 0 | {0, −1000} | P1 |

### 4.3 四项优先级的具体机制

**P0 —— 单方向等待时间不超过 120s（最高，硬保证）**

- 计时：边缘计算机返回该方向等待车辆 ≥1 辆时开始累计 `W`（复用 QueueEstimator 的 `first_seen_at` 代理）。
- 软预警：`W ∈ [80, 120)` 时 S_wait 二次爬升，使其在分数上**先于绿波**胜出（S_wait 最大 +5 > S_gw +2）。
- **硬抢占（关键）**：当 `W ≥ D − (max(0, T_min_green_当前 − 已绿时长) + T_yellow + T_all_red)`，即
  「剩余时间不足以让当前相位走完剩余最小绿、再完成黄灯/全红清空」时，**不走评分、不经 15s 倒数**，
  直接调度该方向（当前相位走完最小绿后立即清空切换），无条件优先，覆盖绿波与普通评分。
  - `T_yellow/T_all_red` 来自审核配置；剩余最小绿按当前相位实时计算，保证 `W + 剩余最小绿 + 清空 ≤ D`。
  - 注意：剩余最小绿也必须计入预算，否则一个刚转绿的当前相位会延迟抢占，导致红灯超时。
- 这是「严格保证等待不超 120s」的正确实现：**靠硬抢占，而非仅靠拉高 score**——
  否则一个过大的绿波权重就可能淹没 P0，造成红灯超时。

**P1 —— 下游溢流保护（次高）**

- 触发：下游路口 YOLO11 返回的下游占用 `O ≥ O_high`（滞回上阈值）→ 该方向 `DOWNSTREAM_BLOCKED`。
- 机制：下游拥堵的方向被**硬排除**出候选（不可被选为下一相位），同时 S_spill = −1000 兜底，防止任何权重把它选出来。
- 解除：`O ≤ O_low`（滞回下阈值，O_low < O_high）才恢复可选，避免抖动。
- **红线**：数据过期/中断时**不得**把「无返回」当作「下游畅通」；下游状态未知时按拥堵处理或进入降级模式。

**P2 —— 主路绿波优先（第三）**

- 仅当路口存在主路、且主路直行相位处于**计划绿波窗口**内、且未被 P0/P1 覆盖时，S_gw = +2.0。
- 绿波是**协调偏好**，不拥有无条件通行权：接近等待截止或错过窗口时应重算，硬约束优先。

**P3 —— 需求评分（第四）**

- 基础分按排队车辆数与等待时间加权，等待车辆多的方向优先通行。
- 输入不应只有车辆数：应含排队长度、等待趋势、置信度与数据新鲜度、消散时间、下游剩余储车空间、当前相位已持续时间。

### 4.4 优先级保证的数值解释

| 冲突场景 | 谁赢 | 依据 |
|---|---|---|
| 主路绿波(+2.0) vs 普通需求(≤1.0) | 绿波 | 2.0 > 1.0 |
| 接近 120s 的支路(>+2.0) vs 主路绿波(+2.0) | 支路 | S_wait 爬升超过 2.0 |
| 下游拥堵方向(−1000) vs 任何相位 | 被排除 | −1000 兜底 + 硬排除 |
| 到 120s 截止 vs 一切 | 强制抢占 | 硬抢占，不经评分 |

> 初值仅供仿真起步，必须通过灵敏度分析与真机数据标定；任何改动不得破坏上述相对次序。
>
> **次序由代码强制**：`ScoreConfig` 构造时校验 `green_wave_score > 需求权重和`、
> `wait_urgency_max_score > green_wave_score`、`|spillback_penalty| > wait_urgency_max_score`，
> 违反即以 `ConfigError` 拒绝加载（默认值已满足）。因此调参无法把 P2/P3 次序调反。

## 5. 最小绿 / 最大绿算法

| 参数 | 语义 | 行为 | 现状 |
|---|---|---|---|
| 最小绿 `min_green_s` | 相位最短放行时长 | 未满足前**禁止切换**（硬约束） | 已在 `safety.py` 与 `state_machine.py` 实现 |
| 最大绿 `max_green_s` | 相位最长放行时长 | 达到后**强制触发切换**（硬约束，防饥饿、界定时长） | 已在 `state_machine.py` 实现 |
| 区间（min, max） | 可响应切换区 | 仅当 `S(candidate) > S(current) + hysteresis` 且持续去抖时间后触发 15s 倒数 | 已在 `state_machine.py` 实现 |

- `hysteresis = 0.1`、`switch_debounce_s = 3.0`（初值）：避免分数抖动导致的频繁切换。
- 最大绿与 P0 协调：最大绿限制当前相位时长，P0 限制方向等待风险，二者不能只靠一个 `if` 解决（见 README 的可行性条件）。

## 6. 15 秒倒数切换状态机（A–E）

在 README 建议的五态上细化，明确「倒数 = 切换请求倒计时」，且全程可复核、可回退：

| 状态 | 说明 |
|---|---|
| **A 绿灯运行** | 当前相位放行，记录绿灯开始、最小绿/最大绿，持续更新等待风险与交通状态 |
| **B 切换请求评估** | 满足下列之一：①候选分数 > 当前 + hysteresis（去抖）；②达到最大绿；③P0/P1 硬触发 |
| **C 15 秒倒数** | 启动 15s 倒数显示（兼容 GA/T 508）。倒数期间**每 tick 复核**：更高优先级出现（P0 硬抢占 / 新下游拥堵 / 绿波窗口变化）→ 重规划；触发条件消失且未达最大绿、无 P0 → 可取消 |
| **D 安全转换** | 倒数结束 → 执行**黄灯（配置值）→ 全红（配置值）**，随后才允许下一合法相位放行 |
| **E 新相位确认** | 收到可信信号机执行反馈才算切换完成；执行失败进入故障处理流程 |

> **安全要点**：15s 是「请求倒计时」不是「绿灯剩余时间」的替代品；黄灯/全红时长来自审核配置；
> 倒数显示与实际清空必须一致，倒计时期间被抢占时不得显示误导性读数。
>
> **注意（关键时序）**：15s 倒数**仅用于「分数驱动的可选切换」**；P0 硬抢占与最大绿必须**直接清空切换、跳过倒数**，
> 否则倒数期间绿灯继续、被服务方向继续等待，会额外占用时间，突破 120s 硬指标或最大绿上限。
>
> 状态 E（执行反馈）由 `feedback.py` 的 `FeedbackMonitor` 实现：切换指令发出后，须在确认超时内收到控制器报告的目标相位；
> 超时、控制器进入 `FAULT`、或落到未请求的相位，均判定执行失败并进入故障流程（固定配时 / 黄闪）。

## 7. 安全红线与已知风险

1. **score 无灯色权限**：只优化排序，不决定亮灯。
2. **先安全后优化**：冲突互锁、切换时序、信号机允许、下游条件 是硬约束（F(t)）。
3. **P0 靠硬抢占**：仅拉高 score 会被更大权重淹没，必须走预定义约束路径。
4. **配时可追溯**：最小绿/最大绿/黄灯/全红/15s 来自审核配置，运行时不临时生成。
5. **执行反馈是权威**：无反馈不更新相位，失败进故障流程。
6. **数据缺失 ≠ 空/畅通**：观测超时或下游无返回时，进入**降级模式**（见 §9），不得当作无车或下游畅通。
7. **冲突表必须核验**：相位冲突关系来自路口审核配置，非算法假设。
8. **标准数值待核验**：GB 25280 等条款必须取得全文并请专业人员确认后使用。

## 8. 数据新鲜度与故障降级（已实现 `degradation.py`）

- 观测超时（`runtime.observation_timeout_s=3.0`）：某方向数据过期时**不得置零**，该方向按「状态未知」处理（`DataFreshness`）。
- 降级策略（`DegradationController`）：
  - 全链路正常（`NORMAL`）：自适应决策（本文档算法）。
  - 部分观测失效（`PARTIAL`）：受影响方向用 `conservative_oldest_wait` 保守估计等待时间（自上次观测起算，从未观测则自启动起算），经 P0 预算继续被服务，仍满足安全约束。
  - 关键数据大范围失效 / 通信中断（`FAILSAFE`）：切换至**固定配时或黄闪**（遵循 GB 25280 故障行为，即控制器进入 `FAULT` 模式），并告警。
- 现有 `safety.reject_stale_observations`、`safety.reject_unknown_phases`、`safety.require_config_validation` 作为基础开关保留并扩展。
