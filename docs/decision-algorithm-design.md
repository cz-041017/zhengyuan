## 0. 项目推进规程（每次执行前必读）

这是一个**安全关键系统**：决策层的缺陷可能引发交通事故。为保障「有序、正确、可追溯」的推进，每次改动前必须执行以下规程，并在改动说明里复述关键结论：

1. **先检索、再推理、后动手**：重读 `README.md`、本文档、`src/traffic_control/` 全部源码、`configs/` 全部配置、`tests/` 全部测试，确认当前实现边界与假设。
2. **明确改动落在哪一层**：模型（models）/ 配置校验（config_loader）/ 状态估计（queue_estimator）/ 安全守卫（safety）/ 评分引擎（scoring）/ 相位状态机（state_machine）。
3. **先安全后优化**：任何评分、绿波、需求优化都**不得绕过**硬约束（冲突互锁、最小绿、最大绿、清空时序、P0 等待截止、P1 下游溢流）。
4. **参数必须可追溯**：黄灯/全红/最小绿/最大绿/相位冲突表必须来自**经审核的路口配置与信号机规则**，运行时禁止由 score 临时生成。
5. **小步提交 + 测试不回归**：每次改动配套单元测试；`uv run pytest` 必须全绿。
6. **改动即更新文档**：涉及算法、配置、安全约束的改动，同步更新本文档与 README 的「现状/路线图」。
7. **不写死未核验值**：涉及国标数值的，标注「待核验全文」，不冒充权威。

## 1. 设计目标、约束与总体思路

### 1.1 要解决的问题

传统定时信号按固定周期轮换，**不感知实际车流**：车少的相位空放绿灯、车多的相位排队溢出。
本决策层的目标：**在保证安全（不冲突、不超时、不出错）的前提下，把绿灯时间尽可能给"最需要"的方向**。

### 1.2 三个硬性约束（不可妥协）

| 约束 | 内容 | 为什么不可妥协 |
|---|---|---|
| **安全** | 冲突相位不能同时放行；切换必须有黄灯/全红清空 | 违反会撞车 |
| **公平** | 任一方向等待不超过 `max_wait_target_s`（默认 120s） | 违反会引发投诉、闯红灯 |
| **可信** | 数据缺失/过期不能当作"没车"；执行结果必须确认 | 违反会做出错误决策 |

### 1.3 设计总思路：**先约束，后优化**

```
① 硬约束过滤  → 得到"当前可以安全放行"的相位集合 F(t)
② 硬抢占判断  → P0 等待截止 / 最大绿到点，走预定义路径（不参与评分）
③ 软评分排序  → 只在 F(t) 内对候选打分，取最高（带滞回与去抖）
④ 切换握手    → （可选换灯走 15s 倒数；P0 抢占/最大绿跳过）→ 黄灯/全红清空 → 新相位 → 等执行反馈
```

**为什么这样分？** 因为「安不安全」和「谁更该走」是两类完全不同的问题：
- 安全问题必须用**确定性规则**（硬约束）回答，不能靠打分"碰运气"；
- 公平/效率问题才适合用**可调权重**（评分）回答。

把两者混在一起（比如"给安全加个大分"）会导致：调大某个权重就淹没了安全约束。
**分层后，安全永远不被权重影响，调参只影响"同等安全条件下谁先走"。**

### 1.4 分层的好处（为什么决策层只提建议、不直接按灯）

决策层输出 `PhaseDecision`（"建议下一相位"），而非灯色指令。好处：
1. **可测试**：算法可以脱离硬件、纯逻辑单测（122 个用例即基于此）；
2. **可替换**：换信号机/仿真器只需改接口层，算法不动；
3. **可审计**：每个决策都有 `reason` 和 `scores`，出问题能追溯"为什么这么判"。

## 2. 相位分组模型

决策层把「交通方向 movement」合并为「信号相位 phase」。一个相位 = 一组**能同时放行且通过冲突校核**的交通流集合。

### 2.1 模式 A：四向均为支路（无主路、无绿波）

每向「直行 + 左转」合并为 1 组，共 **4 组**，全部通过 score 对比：

| 组（相位 ID） | 放行方向 | 评分方式 |
|---|---|---|
| `P_N` | 北向 直行 + 左转 | score |
| `P_E` | 东向 直行 + 左转 | score |
| `P_S` | 南向 直行 + 左转 | score |
| `P_W` | 西向 直行 + 左转 | score |

### 2.2 模式 B：存在城市主路（设主路为南北向，方向可配置）

| 组 | 放行方向 | 评分方式 |
|---|---|---|
| P_MT | 主路**双向直行**（北直 + 南直） | **绿波优先（P2）** |
| P_ML | 主路**双向左转**（北左 + 南左） | score 比对（P3） |
| P_E | 东支路 直行 + 左转 | score 比对（P3） |
| P_W | 西支路 直行 + 左转 | score 比对（P3） |

> **实现状态**：`green_wave.*` 5 个参数已定义并通过配置校验，但**运行时窗口计算尚未接线**
> （仿真台 `panan_bridge.py` 硬编码 `green_wave_active=False`，`runtime.py` 不读取绿波参数）。
> 因此 P2 绿波**当前不生效**，`P_MT` 实际只按 P3 需求评分。

### 2.3 为什么这样分组（设计逻辑与好处）

- **直行+左转合并**：同一个来向的直行与左转通常不互相冲突（左转让对向直行是另一回事），合并后相位更少、切换更少、损失时间更少。
- **但前提必须校核**：能否合并进同一相位，取决于**该路口经审核的相位冲突表**是否把这两股流列为互斥；
  若冲突表判定互斥，必须拆成独立相位。**冲突关系必须来自经审核的路口配置**，算法不自行推断——冲突判错就是撞车。
- **主路单独成组**：主路车流大，单独给绿波组可减少主路停车次数（P2 的由来）。
- **好处**：相位数量可控（4 组），切换开销小；同时保留"主路优先"的可配置能力。

## 3. P0–P3 优先级模型（核心）

优先级语义顺序：**P0 > P1 > P2 > P3**。它不是单条数值刻度，而是「结构优先级」：
**P0/P1 主要由硬约束 + 硬抢占保证，score 只作为预警/兜底。**

### 3.1 每方向（每组）的输入量

- `N`：排队车辆数（感知层停止线前等待计数，经 QueueEstimator 聚合）
- `W`：该方向**最老等待时间** `oldest_wait_s`（秒，≥1 辆车时开始累计）
- `O`：下游路口拥堵观测值
- `D` = 120s（`optimization.max_wait_target_s`，等待硬指标）

组的聚合：`N_p = Σ(成员方向 N)`，`W_p = max(成员方向 W)`；
`O_p` 在评分层面按"任一成员方向下游拥堵即压制"处理（`SpillbackMonitor` 逐车道维护，
仿真桥接用 `any(blocked)`，未做 `max` 数值聚合）。

### 3.2 相位评分公式（初值，待标定）

```
S(p) = S_demand(p) + S_gw(p) + S_wait(p) + S_spill(p)
```

| 项 | 公式（初值） | 取值范围 | 优先级 |
|---|---|---|---|
| S_demand（P3 需求） | `0.6·min(N/N_max,1) + 0.4·min(W/D,1)`，N_max=20 | [0, 1] | P3 |
| S_gw（P2 绿波） | 主路直行相位处于绿波窗口内时 `+2.0`，否则 0 | {0, +2.0} | P2 |
| S_wait（P0 软预警） | `5.0 · clip((W − 80)/40, 0, 1)²` | [0, +5.0] | P0 |
| S_spill（P1 硬压制） | 任一下游方向拥堵时 `−1000`，否则 0 | {0, −1000} | P1 |

### 3.3 四项优先级的具体机制（含"为什么"）

**P0 —— 单方向等待时间尽量不超过 120s（最高，尽力保证 best-effort）**

- **计时**：感知层返回该方向等待车辆 ≥1 辆时开始累计 `W`。
- **软预警**：`W ∈ [80, 120)` 时 S_wait 二次爬升，使其在分数上**先于绿波**胜出（S_wait 最大 +5 > S_gw +2）。
- **截止抢占（关键）**：当 `W ≥ D − (max(0, T_min_green_当前 − 已绿时长) + T_yellow + T_all_red)`，
  即"剩余时间不足以让当前相位走完剩余最小绿、再完成黄灯/全红清空"时，**不走评分、不经 15s 倒数**，
  直接调度该方向（当前相位走完最小绿后立即清空切换）。
- **为什么必须用截止抢占而不是"加大分数"**：
  如果只靠加分，一旦绿波权重或需求权重调得更大，P0 就会被淹没，某方向可能等超过 120s。
  截止抢占是一道"无论权重怎么调都绕不过去的闸门"。
- **为什么要把"剩余最小绿 + 清空"计入预算**：否则一个刚转绿的当前相位会让抢占延迟，导致红灯超时。
- **诚实边界（与实现一致，必须如实说明）**：
  1. **最小绿优先于抢占**：`state_machine.py` 在 `elapsed < min_green_s` 时直接返回
     `minimum_green_not_met`（`feasible=True`），**即使已到 120s 也不切换**。
     因此 120s 是"尽力保证"，不是绝对硬保证（实际等待可能略超）。
  2. **P0/P1 冲突**：若"到截止的方向"恰好"下游拥堵"（`blocked_deadline` 非空），
     返回 `PhaseDecision(None, "p0_p1_conflict", feasible=False)`，**不切换**，由上层上报/仲裁。
     这不是"伪造相位强行放行"，而是安全优先的显式拒绝。

**P1 —— 下游溢流保护（次高）**

- **触发**：下游占用 `O ≥ O_high`（滞回上阈值）→ 该方向 `DOWNSTREAM_BLOCKED`。
- **机制**：下游拥堵的方向被**硬排除**出候选，同时 S_spill = −1000 兜底，防止任何权重把它选出来。
- **解除**：`O ≤ O_low`（滞回下阈值，O_low < O_high）才恢复可选，避免抖动。
- **为什么用"硬排除 + 大负分"双保险**：硬排除保证安全，大负分保证即使逻辑有 bug 也不会误选。
- **红线**：数据过期/中断时**不得**把"无返回"当作"下游畅通"；未知按拥堵处理。

**P2 —— 主路绿波优先（第三，当前未接线）**

- 仅当路口存在主路、且主路直行相位处于**计划绿波窗口**内、且未被 P0/P1 覆盖时，S_gw = +2.0。
- **实现状态**：`green_wave_eligible` / `Scorer.green_wave_active` 只有单元测试置 `True`，
  生产路径（`runtime.build_runtime`、`panan_bridge.py`）**从未计算绿波窗口**；该加分当前恒为 0。
- **为什么只是"加分"而不是"硬优先"**：绿波是"协调偏好"，用来减少主路停车；
  但它**不应拥有无条件通行权**——接近等待截止或错过窗口时必须让位，否则支路会饿死。

**P3 —— 需求评分（第四）**

- 基础分按排队车辆数与等待时间加权，等待车辆多的方向优先通行。
- **为什么用"车数 60% + 等待 40%"**：纯车数会忽视"等得久"的车；纯等待会让刚到的车流被压。
  两者加权是折中，且权重可调（见参数手册）。

### 3.4 优先级保证的数值解释（冲突场景裁决表）

| 冲突场景 | 谁赢 | 依据 |
|---|---|---|
| 主路绿波(+2.0) vs 普通需求(≤1.0) | 绿波 | 2.0 > 1.0 |
| 接近 120s 的支路(>+2.0) vs 主路绿波(+2.0) | 支路 | S_wait 爬升超过 2.0 |
| 下游拥堵方向(−1000) vs 任何相位 | 被排除 | −1000 兜底 + 硬排除 |
| 到 120s 截止 vs 一切 | 尽力抢占（最小绿走完后） | 不走评分，但仍受最小绿挡板约束 |

> 初值仅供仿真起步，必须通过灵敏度分析与真机数据标定；**任何改动不得破坏上述相对次序**。

## 4. 最小绿 / 最大绿算法

| 参数 | 语义 | 行为 | 为什么 |
|---|---|---|---|
| 最小绿 `min_green_s` | 相位最短放行时长 | 未满足前**禁止切换**（硬约束） | 防"刚绿就红"，保证行人和安全起步 |
| 最大绿 `max_green_s` | 相位最长放行时长 | 达到后**强制触发切换**（硬约束） | 防某方向长期霸占绿灯导致其他方向饿死 |
| 区间（min, max） | 可响应切换区 | `S(candidate) > S(current) + hysteresis` 且持续去抖 → 触发 15s 倒数 | 让"有更好选择时"可以提前换 |

- `hysteresis = 0.1`、`switch_debounce_s = 3.0`（初值）：避免分数抖动导致频繁切换（频繁切换会损失大量绿灯时间）。
- 最大绿与 P0 协调：最大绿限制当前相位时长，P0 限制方向等待风险，**二者不能只靠一个 `if` 解决**（见 §8 时序分析）。

## 5. 15 秒倒数切换状态机（A–E）

| 状态 | 说明 |
|---|---|
| **A 绿灯运行** | 当前相位放行，记录绿灯开始、最小绿/最大绿，持续更新等待风险 |
| **B 切换请求评估** | 满足之一：①候选分数 > 当前 + hysteresis（去抖）；②达到最大绿；③P0 截止抢占。**P1 不直接触发切换**：下游拥堵只把候选从"可选集合"排除；当前相位若本身位于拥堵下游方向，仍走正常去抖/最大绿流程 |
| **C 15 秒倒数** | 启动 15s 倒数显示（兼容 GA/T 508；**当前实现不提供"剩余秒数"接口**，无法直接驱动倒计时显示屏）。倒数期间**每 tick 只复核已挂起的候选**：触发条件消失且未达最大绿、无 P0 → 可取消；若出现 P0 截止，则按抢占路径直接清空切换（不在倒数中改选其它候选） |
| **D 安全转换** | 倒数结束 → 执行**黄灯（配置值）→ 全红（配置值）**，随后才允许下一合法相位放行 |
| **E 新相位确认** | 收到可信信号机执行反馈才算切换完成；执行失败进入故障处理流程 |

> **关键时序（安全红线）**：15s 倒数**仅用于「分数驱动的可选切换」**；
> P0 截止抢占（最小绿走完后）与最大绿必须**直接清空切换、跳过倒数**，否则倒数期间绿灯继续、被服务方向继续等待，
> 会额外占用时间，突破 120s 硬指标或最大绿上限。
>
> **为什么保留 15s 倒数**：①兼容 GA/T 508 倒计时显示器；②给"可选的换灯"一个确认窗口，避免误切换。
> **为什么硬抢占必须跳过它**：倒数是"可选的等待"，而 P0 是"不能等的截止"——两者语义相反，不能混用。

## 6. 数据新鲜度与故障降级

> **实现状态**：`degradation.py` 的三种状态与保守等待已实现并有单元测试；
> **`DecisionLayer` 门面已接线**（`layer.tick()` 内部跑降级，返回 `result.degradation`）；
> 但**仿真台 `panan_bridge.py` 仍直接调 `state_machine.tick()`、未走门面**，
> 因此仿真中降级策略不生效（属仿真台接线缺口，非决策层缺口）。

### 6.1 三种运行状态

| 状态 | 触发条件 | 应对方案 |
|---|---|---|
| `NORMAL` | 全链路数据新鲜 | 正常自适应决策（本文档算法） |
| `PARTIAL` | 部分方向数据过期 | 受影响方向用 `conservative_oldest_wait` **保守估计**（自上次观测起算，从未观测则自启动起算），经 P0 预算继续被服务 |
| `FAILSAFE` | 关键数据大范围失效 / 通信中断 | 切换至**固定配时或黄闪**（遵循 GB 25280 故障行为，控制器进入 `FAULT` 模式）并告警 |

### 6.2 为什么这样设计（设计逻辑）

- **为什么"数据缺失 ≠ 没车"**：如果摄像头断线、决策层把"没数据"当成"没车"，就会一直放行别的方向，
  导致这个方向永远不绿——这是**比"慢一点"严重得多的事故**。所以缺失必须按"未知/最坏"处理。
- **为什么用"保守等待"而不是"清零"**：保守等待（自上次观测起算）至少不会低估等待时间，能触发 P0 兜底。
- **为什么要有 FAILSAFE**：当完全失去感知，任何"智能决策"都是瞎猜；退回固定配时是**已知安全的兜底**。

> 但仿真台 `panan_bridge.py` **未消费** `FeedbackStatus`，因此仿真中执行失败不会触发故障流程（仿真台接线缺口）。

- 决策层发出"建议下一相位"后，信号机须在**确认超时**内回传目标相位。
- **超时 / 控制器故障 / 相位错配 → 判执行失败**，进入故障流程（固定配时 / 黄闪）。
- **为什么必须有反馈**：决策层与信号机是两套系统，指令可能丢失、执行可能失败。
  若"以为灯变了其实没变"，决策层会基于错误状态继续决策——**这是典型的"闭眼开车"**。

## 8. 最坏情况时序分析（部署前的可行性证明）

`timing_analysis.py` 在部署前计算：
- **120s 是否结构可行**：最大切换开销（清空 + 最短绿灯）能否塞进 120s 预算；
- **无抢占最坏等待**：如果所有方向都在排队，最坏要等多久；
- **preempt 负载**：有多少相位只能靠 P0 抢占才不超时。

**为什么必须做**：如果"无抢占最坏等待"远超 120s，说明 120s 全靠抢占兜底——
这不是"保证"，而是"运气"。正确做法是**缩短最大绿**，让 120s 成为结构性保证，而非依赖抢占。

## 9. 各种场景的应对方案（一览表）

| 场景 | 决策层怎么应对 | 依据章节 |
|---|---|---|
| 正常平峰 | 按 P3 需求评分正常轮换 | §3.2 |
| 某方向车特别多 | P3 分数高，优先放行 | §3.2 |
| 某方向等待接近 120s | P0 软预警爬升 → 到截止抢占（最小绿优先） | §3.3 |
| 下游路口已堵 | P1 硬排除该方向 + −1000 兜底 | §3.3 |
| 主路要绿波 | P2 +2.0（可被 P0 覆盖） | §3.3 |
| 部分摄像头断线 | PARTIAL 保守估计等待，P0 继续兜底 | §6 |
| 全部数据中断 | FAILSAFE 固定配时/黄闪 | §6 |
| 信号机不执行/回错相位 | 判执行失败，进故障流程 | §7 |
| 最短绿灯刚到 | 禁止切换（保护行人/安全起步） | §4 |
| 最长绿灯到点 | 强制切换（防饿死） | §4 |
| 绿波与等待冲突 | 等待优先（P0 > P2） | §3.4 |
| 分数抖动 | 滞回 + 去抖，避免频繁切换 | §4 |

## 10. 安全红线与已知风险

1. **score 无灯色权限**：只优化排序，不决定亮灯。
2. **先安全后优化**：冲突互锁、切换时序、信号机允许、下游条件 是硬约束（F(t)）。
3. **P0 靠截止抢占（受最小绿约束）**：仅拉高 score 会被更大权重淹没，必须走预定义约束路径；
   但最小绿优先，故 120s 是尽力保证而非绝对硬保证。
4. **配时可追溯**：最小绿/最大绿/黄灯/全红/15s 来自审核配置，运行时不临时生成。
5. **执行反馈是权威**：无反馈不更新相位，失败进故障流程。
6. **数据缺失 ≠ 空/畅通**：观测超时或下游无返回时进入降级模式，不得当作无车或畅通。
7. **冲突表必须核验**：相位冲突关系来自路口审核配置，非算法假设。
8. **标准数值待核验**：GB 25280 等条款必须取得全文并请专业人员确认后使用。

## 11. 设计权衡与整体好处（总结）

| 设计选择 | 代价 | 好处 |
|---|---|---|
| 决策层只提建议、不按灯 | 多一层接口 | 可测试、可替换、可审计 |
| 先硬约束后评分 | 逻辑更复杂 | 调参永不破坏安全 |
| P0/P1 用硬规则而非加分 | 不能"用调参解决一切" | 安全兜底不被权重淹没 |
| 数据缺失按未知处理 | 可能偏保守 | 绝不因丢数据造成事故 |
| 15s 倒数仅用于可选切换 | 需区分两类切换 | 兼容倒计时显示且不拖慢硬抢占 |
| 配时来自审核配置 | 部署前需人工核验 | 参数可追溯、责任清晰 |

> **一句话**：本设计把"安全"和"效率"解耦——安全用**不可绕过的硬规则**保证，
> 效率用**可调的评分**优化。这样无论怎么调参，最坏情况（撞车、超时、丢数据）都有兜底。

## 14. 标定与验证计划（部署前置）

1. **仿真验证**：用 `configs/simulation.yaml` 驱动，验证 P0≤120s 恒成立、P1 无溢流、绿波带宽、最小/最大绿、15s 倒数时序。

4. **真机联调**：仅在仿真与最坏情况分析通过后，先在受控测试路口联调，取得标准全文并经专业人员确认后部署。
